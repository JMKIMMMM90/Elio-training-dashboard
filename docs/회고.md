# 회고 — 성과발표회 공유용

> AI(Claude Code)와 함께 신입교육 대시보드를 만든 과정의 기록. 계속 갱신한다.

## 무엇을 만들었나

비전공자(기획자) 1인이 AI 페어로 **1주일(9/1~9/7)** 만에:
- 신입교육 진척·평가 관리 웹앱 (실시간 DB·파일 제출·자동 채점·역할별 화면)
- 회사 디자인 시스템 적용, 500점 평가 체계 설계, 관리자 노코드 운영 도구
- 별도 서버·빌드 도구 없이 무료 인프라(GitHub Pages + Firebase 무료 한도)로 운영

## 작업 방식 (잘 작동한 루프)

**논의 → 확정 → 구현 → 배포 → 실화면 검증 → 다음 논의**

1. 기능을 바로 만들지 않고 먼저 설계안·트레이드오프를 논의해 확정 (예: 저장 방식 3안 비교, 배점 체계 3안 비교)
2. AI가 구현·배포하고, **배포된 실제 사이트에서 테스트 계정으로 검증**까지 마친 뒤 보고
3. 실사용 화면을 보고 리뷰 포인트를 던지면 다음 사이클 시작

핵심: **사용하면서 설계가 진화**했다. 처음 스펙을 다 정하려 하지 않고, 매일 실제 화면·실사용 데이터(신입이 실제로 입력한 것)를 보고 다음 요구를 구체화했다.

## 시간을 많이 쓴 곳 (관찰)

| 구간 | 비중 | 메모 |
|---|---|---|
| 평가 체계 설계 논의 | 높음 | 배점·가점·상징성(500점) — 시스템의 뼈대라 시간 쓸 가치가 있었음 |
| 외부 서비스 셋업 (Firebase 콘솔) | 중간 | 콘솔 UI가 계속 바뀌어 스크린샷 주고받으며 진행. AI가 화면을 보고 짚어주니 해결 |
| UI 디테일 반복 수정 | 중간 | 아이콘→텍스트 버튼, 줄바꿈 등 — 실화면을 봐야만 나오는 이슈들 |
| 기능 구현 자체 | 낮음 | AI가 담당. 사람은 방향·검수에 집중 |

## 배운 것

1. **평가 요소를 먼저 확정해야 시스템이 선다** — 화면·기능은 배점 체계가 정해지자 자연스럽게 따라왔다.
2. **자동화의 단위는 "사람이 입력할 숫자를 줄이는 것"** — 달성률·제출시점·FINAL 채점을 수식화하니 담당자 입력이 주당 숫자 4개+코멘트로 줄었다.
3. **신입이 컨트롤 가능한 지표는 실시간으로 보여야 움직인다** — "지금 제출하면 +3점" 같은 즉각 피드백이 행동을 만든다.
4. **첫 화면은 참조가 아니라 행동** — 설명 문서를 다 첫 화면에 쌓으면 아무도 안 읽는다. 빈도로 분리(홈/안내/목표/평가).
5. 공개 저장소에는 회사 원본 자료를 절대 넣지 않는다 (Pages 호스팅 = public).

## 다음번에 더 잘하려면

- 평가 체계·명칭 등 "뼈대 결정"을 프로젝트 초반에 몰아서 확정하면 재작업이 줄어든다 (이번엔 점진 확정으로 배점을 3번 개편).
- 외부 콘솔 작업(Firebase 등)은 스크린샷 기반 페어링이 가장 빨랐다 — 처음부터 그렇게 할 것.
- 교육 데이터가 쌓이는 구조(오류 로그 등)를 처음부터 설계하면, 교육 운영이 곧 회사 자산(서식 규칙서) 축적이 된다 — 다음 단계(/신입평가 스킬)의 핵심 설계.
